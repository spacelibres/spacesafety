## 二、分析型目标（Analyst Sat）

传感器看到已知目标附近的物体却无法确认身份时，会被放到预留号段并命名 `N - Analyst Sat`。
**有真实轨道根数，没有国际编号，没有所有者。**

分布在三个号段，共 **1,112 个**：

| 号段 | 数量 |
|---|---|
| 80000–89999 | 683 |
| 270000–279999 | 401 |
| 290000–299999 | 28 |

筛选条件是 `name LIKE '%Analyst Sat%'`，**不是号段**。曾用 `norad_id >= 270000`，
只拿到 429 个，漏掉的 683 个让 KeepTrack 看起来独有一批未知目标。

## 四、硬体半径（Pc 计算的关键几何量）

### 总体覆盖

| 项 | 数量 | 占比 |
|---|---|---|
| 有值 | 38,664 | 53.4% |
| 缺失 | 33,737 | 46.6% |

### 缺口没有看上去那么大

| 缺口的构成 | 数量 | 是否影响在轨计算 |
|---|---|---|
| 已再入对象 | 32,198 | 否 |
| **仍在轨** | **1,539** | **是** |

### 在轨缺口的 1,539 个是什么

| 类别 | 数量 | 能否补齐 |
|---|---|---|
| 分析型目标 | 1,111 | **不能**——身份未知，不会有物理模型 |
| Space-Track 有记录 | 337 | 理论可能，见下 |
| 仅 KeepTrack / DISCOS 有 | 91 | 无模型来源 |

### 能否从其他字段推算

标准做法是按等面积球折算半径。实测这 337 个里：

| 可用字段 | 可用数量 |
|---|---|
| DISCOS 横截面积 | 0 |
| Spacebook 横截面积 | 0 |
| DISCOS 直径 | 0 |
| Spacebook 直径 | 0 |
| KeepTrack 直径 | **1** |

**337 个里只有 1 个能推算。**

### 为什么 Spacebook 有 281 个记录却没有半径

抽查（NORAD 51、52、53、115、119……）：

```
name__spacebook = "ECHO 1 DEB (MYLAR OBJ)"
hard_body_radius_m__spacebook = NULL
mass_kg__spacebook = NULL
```

**Spacebook 收录了这些对象，但没给它们建模物理量**——质量和半径同时为空。
不是我们解析丢失，是上游本身没有。

### 结论

在轨缺硬体半径的 1,539 个对象中：

- **1,111 个永远补不上**（分析型目标，无身份）
- **337 个上游没有模型**，只有 1 个能用直径推算
- **91 个没有模型来源**

**这个缺口当前无法通过现有四个数据源补齐。** 要补只能引入新的模型数据源。

核对脚本：

```bash
npx tsx tools/hbr-gap-audit.ts       # 总覆盖、已再入/在轨拆分、可推算式
npx tsx tools/hbr-gap-detail.ts      # 缺口按分类/来源/制造商分布与样本
npx tsx tools/hbr-gap-candidates.ts  # 337 个候选者能否从其他字段推算
```

## 五、统计口径的坑（记录在案）

判断「某来源有没有这个对象」，**必须检查该来源的全部列**。

第一次只用 `name` / `cospar_id` / `inclination_deg` 三四列统计，报出 90 个「四源全空」对象。
实际 Spacebook 持有它们的名字，只是名字在没被检查的列里。

宽表里某来源的列有几十个，漏任何一个都会造成误判。

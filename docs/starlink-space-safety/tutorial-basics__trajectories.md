# Trajectories

A trajectory is a series of state vectors (position, velocity, time and covariance) related to a single object. Depending on the file format, it may contain other metadata as well.

In the web interface, a trajectory details page includes metadata about the trajectory, a plot of the orbital elements of the trajectory's states, and any CDMs that have been generated against the trajectory:

## Trajectory Submission Types ​

The `POST /api/v1/trajectory` API endpoint and the user interface require that an operator submits trajectories with an `upload_type` parameter, which is one of two options, described below:

**Definitive** trajectories indicate the trajectory a satellite is intended to fly. It is shared with all the users of the system, and the screening system's catalog assumes that the most-recently-submitted definitive trajectory is the best estimate for where an object is going to be.

**Hypothetical** trajectories provide a mechanism for operators to do one-off screening of maneuvers without updating an object's definitive trajectory or confusing other operators. They aren't inserted into the catalog for future trajectory submissions to screen against, and they (and their results) are only visible to the submitting operator.

To summarize:

| Upload Type | Use Case | Catalog Semantics | Permissions |
| --- | --- | --- | --- |
| definitive | A trajectory that an operator is planning to fly. | Inserted into the catalog, replacing the previously-uploaded definitive trajectory for the object if it exists. | Trajectory and associated events / CDMs are viewable by all users |
| hypothetical | A trajectory that an operator is considering flying, but would like to screen first. | Screened once, but not inserted into the catalog. | Trajectory and associated CDMs only viewable by submitting operator. No events are created. |

## Trajectory State Sources ​

Each trajectory also has a `state_source` field, which indicates the data source that produced the trajectory:

| State Source | Meaning |
| --- | --- |
| operator_ephemeris | Trajectory was submitted by the operator of the spacecraft using the API |
| spacex_optical | Trajectory was based on optical data from the Stargaze Space Situational Awareness system. |

Users may view all `operator_ephemeris` trajectories in the system, their metatadata, and all CDMs/events generated based on them.

Users may view the CDMs, events, and metadata generated by `spacex_optical` trajectories against their own submitted ephemeris, but may not inspect the contents of `spacex_optical` trajectories directly.

## Trajectory Requirements ​

### Structure ​

In order to efficiently screen the catalog, we enforce the following constraints on trajectory files:

- We recommend submitting your trajectory file with covariance although it is not required. (See Note below.)
- Trajectory files must have at least 6 state vectors in the future
- Trajectory files must span less than 21 days
- Trajectory files must span a minimum 42 seconds
- Trajectory files must have reasonable position (i.e., not below the earth's surface) and velocity (not exceeding 70km/s) values
- Trajectory files must be in a supported reference frame and time system

If an operator submits a trajectory file that violates any of these requirements, they will receive an HTTP 400 (Bad Request) response with a helpful error message.

These are minimal requirements that the system imposes to mathematically perform interpolation and screening. However, for operational purposes, we recommend submitting ephemeris files spanning several days, so that operators can react to CDMs with adequate lead time.

### Covariance ​

If covariance matrices are provided then every state vector must have an associated positive semi-definite covariance matrix. If no covariance is provided then Collision Probability will not be generated for conjunctions against this trajectory and the CDM file will have a NULL value for the `COLLISION_PROBABILITY` field (This diverges from the CDM CCSDS standard).

## Supported Formats ​

Our system supports OEM (Orbital Ephemeris Message), OCM (Orbital Comprehensive Message), Modified ITC, UTC, and NASA formats for trajectories.

Today, we only support CCSDS files in KVN (Key Value Notation), not XML.

If a file starts with "CCSDS_OEM_VERS", the system attempts to parse it as an OEM file. If a file starts with "CCSDS_OCM_VERS", the system attempts to parse it as an OCM file. If the file contains the headers "time", "pos.x", and "vel.x" as the ephemeris data field headers, the system attempts to parse it as a UTC file. Otherwise, it attempts to parse it as a Modified ITC file.

### OEM (Orbital Ephemeris Message) ​

OEM (Orbital Ephemeris Message) format is defined in Section 5, and Section 7.7.2, of the CCSDS spec ([link](https://public.ccsds.org/Pubs/502x0b3e1.pdf))

We accept a subset of OEM-formatted trajectories, subject to the supported reference frames and time systems (below) and the general trajectory requirements.

### OCM (Orbital Comprehensive Message) ​

OCM (Orbital Comprehensive Message) format is defined in Section 6 of the CCSDS spec ([link](https://public.ccsds.org/Pubs/502x0b3e1.pdf)).

We accept a subset of OCM-formatted trajectories, subject to the supported reference frames and time systems (below) and the general trajectory requirements.

#### Additional OCM Restrictions ​

Data sections not mentioned below are ignored.

##### Header (CCSDS Table 6-2) ​

Required. Adheres to the requirements for mandatory fields in the spec.

##### Metadata (CCSDS Table 6-3) ​

Must occur exactly 1 time in an OCM file. Adheres to the requirements for mandatory fields in the spec.

##### Trajectory State Time History (CCSDS Table 6-4) ​

Must occur exactly 1 time in an OCM file.

| Keyword | Accepted values | Notes |
| --- | --- | --- |
| TRAJ_REF_FRAME | ITRF , ITRF2000 , EME2000 | Required. |
| TRAJ_UNITS | [km,km,km,km/s,km/s,km/s] | Defaults to [km,km,km,km/s,km/s,km/s] if unspecified. |
| TRAJ_TYPE | CARTPV | Defaults to CARTPV if unspecified. |

All other trajectory keywords are allowed but ignored.

#### Covariance Time History (CCSDS Table 6-6) ​

Must occur 0 or 1 times in an OCM file.

| Keyword | Accepted values | Notes |
| --- | --- | --- |
| COV_REF_FRAME | ITRF , ITRF2000 , EME2000 | Required. |
| COV_ORDERING | LTM | Defaults to LTM if unspecified. |

All other covariance keywords are allowed but ignored.

#### Maneuver Time History (CCSDS Table 6-7) ​

Optional section, may occur 0 or more times in an OCM file. This section cannot occur more than 500 times.

| Keyword | Accepted values | Notes |
| --- | --- | --- |
| MAN_REF_FRAME | NTW_ROTATING | Required. |
| MAN_BASIS | PLANNED | Defaults to PLANNED if unspecified. |
| MAN_COMPOSITION | [TIME_ABSOLUTE, MAN_DURA, ACC_X, ACC_Y, ACC_Z] | Required. Any composition values other than those listed are unsupported. |
| MAN_UNITS | n/a s km/s**2 | Defaults to values listed if unspecified. |

#### Reference Frame and Time Systems ​

SpaceX supports a subset of the reference frames and time systems outlined in the OEM format.

For position and velocity, we support:

- ITRF
- EME2000

Note the supported covariance reference frames diverge from the OEM standard which requires `COV_REF_FRAME`, if specified, to be one of RTN, RSW, TNW; however, the standard also says if `COV_REF_FRAME` is not provided then the covariance matrices shall be specified in the reference frame of the position and velocity. For this reason we support the following covariance reference frames:

- RTN
- ITRF
- EME2000

If `COV_REF_FRAME` is specified then it currently must be specified for every covariance matrix. Covariance timestamps should have a 1-to-1 mapping with state vector timestamps, so a covariance matrix should be present for every position. There may be more covariance matrices than position states, but this is not recommended and the additional matrices will be ignored.

The preferred reference frame for position and velocity is ITRF as this is the native frame that the system uses during screening.

Timestamps must be in UTC in a date time string format as specified by the OEM standard. The standard for OEM files suggests GPS time is supported, but does not specify a format for this field and thus is not currently supported.

### Modified ITC Format ​

Modified ITC format is described in the 18th Space Control Squadrons [SpaceFlight Safety Handbook](https://www.space-track.org/documents/Spaceflight_Safety_Handbook_for_Operators.pdf), p. 19.

It consists of three header lines (which can contain any information), the covariance reference frame (which must be either UVW or EME2000), and then blocks of 4 lines, each with 7 space-separated elements.

The the first line in each block contains a timestamp in yyyyDOYhhmmss.sss format, followed by 3 values representing position (in kilometers) and 3 values representing velocity (in kilometers per second).

The next three lines in each block contain the 21 covariance values that comprise the 6x6 lower triangular of the position and velocity covariance matrix.

## Trajectory Screened Status ​

Each trajectory has an associated status, which starts as `not screened`. Success or intermediate errors can result in the following statuses:

| Status | Meaning |
| --- | --- |
| screened | Trajectory successfully processed. |
| not screened | Not yet processed (default). |
| superseded | Trajectory was not screened because there was a newer definitive trajectory for that object in the same screening cycle. |

### Superseded Trajectories ​

If there are multiple definitive trajectories for the same object downloaded in a single screening cycle, only the newest (by upload time) will be screened. New definitive trajectories for an object will also replace older definitive trajectories for the same object from previous cycles.

## SpaceX Trajectory Uploads ​

Starlink uploads ephemerides for every satellite in its constellation to the production `space-safety.starlink.com` roughly every 60 minutes, with a 7 day time horizon, subject to change due to operational considerations.

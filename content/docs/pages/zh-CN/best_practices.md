# 空间安全最佳实践

下面说的是：怎么用这个服务，才能让它给出的答案值得据以行动。

## 轮询流，不要爬全库

`GET /api/v2/cdm` 必须带限定条件。这是故意的：一个"什么都拉"的客户端既给服务加压，
又收到一堆它处置不了的数据。轮询你自己名下的东西。

```bash
curl --key client.key --cert client.crt \
  'https://<host>/api/v2/cdm?operator1_id=<uuid>&only_active=true&token=<cursor>'
```

记住游标，从停下的地方继续。每次从头读会反复读历史，最终撞上游标的年龄上限。

## 要节奏，不要空转

| 数据 | 合理节奏 | 原因 |
|---|---|---|
| 你自己星历的 CDM | 分钟级 | TCA 的变化跟着星历更新的尺度，不是秒级 |
| 上传后的星历元数据 | 取一次，带退避 | 筛查是排队做的，每秒轮询只是烧配额 |
| CDM 原始文件 | 真需要时才取，一条一次 | 它是同一批事实里最大的表示 |

`503` 时遵守 `Retry-After`。在限流响应之后立刻重试，是客户端把自己的一次限流变成
一次故障的方式。

## 分清"没有交会"和"没有数据"

三种完全不同的情况在界面上长得一样，绝不能一视同仁：

| 状态 | 看上去 | 该怎么办 |
|---|---|---|
| 返回空 `result` | 没有 CDM | 就服务掌握的数据而言，没有东西靠近 |
| `probability_of_collision: null` | 有 CDM 但没有 Pc | 真实交会，概率未知——最近距离仍然有意义 |
| `screened_status: not_screened` | 星历在，但没 CDM | 筛查还没做；"没有告警"此刻不代表任何事 |

## 报问题时带上标识

觉得不对时，带 `correlation_id`（针对某一次失败请求）和 CDM 的 `id`（针对某一条可疑
结果）。没有它们，报的就是一个没人能追溯的症状。

## 留住原始材料

把你上传的和你被告知的都存下来。两个运营方之间讨论交会，靠的是比对输入与算出的输出；
如果只留了结论，事后谁都做不了这件事。

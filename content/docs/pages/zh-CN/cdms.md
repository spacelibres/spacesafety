# CDM

一条交会数据消息（CDM）就是一次筛查结果：两个物体、一个最接近时刻、一个最近距离，
以及在输入允许时——一个碰撞概率。

## 一条里有什么

| 字段 | 含义 |
|---|---|
| `id` | 这条消息本身 |
| `event_id` | 它所属的那个交会，多条 CDM 共享一个 |
| `creation_time` | 这次筛查产出的时刻 |
| `tca_gps_nanos` | 最接近时刻，GPS 纳秒，字符串 |
| `probability_of_collision` | Pc，或 `null` |
| `trajectory1_id` / `trajectory2_id` | 被筛查的两条星历 |
| `object1_*` / `object2_*` | 两个物体，反范式存储，使单行可独立阅读 |
| `is_active` | 是否已被更晚的消息取代 |

## Pc 比你想的更常是 `null`

Pc 需要两边都有协方差。缺了就写 `null`，**绝不写 0**。这个区别要紧：`0` 表示"算过，
可以忽略"，`null` 表示"没算"。把两者一视同仁的客户端，会把一个真实但未知的威胁
排到所有实测值之下。

这种情况下仍然报最近距离，而且它仍然可用：71 米就是 71 米，不管有没有人能给出概率。

## 修订

估计一变，同一个交会就再产出一条 CDM。流会按时间返回全部，因为这段历史正是要点：

```
05:32  Pc 0.0028698   距离 85 km
00:23  Pc 0.0032998   距离 71 km
05:37  Pc 0.0032998   距离 71 km   ← 当前
```

把它读成四次独立告警是经典错误。这是**一个**交会，它的估计在变好。

| 你想要 | 这样取 |
|---|---|
| 每条消息，看估计怎么变 | `/api/v2/cdm?trajectory_id=…` |
| 只要当前估计 | 加 `only_active=true` |
| 某个交会的完整历史 | `/api/v2/event/:id` |

## 取用

```bash
# 涉及某条星历的当前 CDM
curl --key client.key --cert client.crt \
  'https://<host>/api/v2/cdm?trajectory_id=<uuid>&only_active=true'

# 序列化后的 CDM 正文，KVN 格式
curl --key client.key --cert client.crt 'https://<host>/api/v1/cdm/<uuid>?format=kvn'
```

## CDM 不是什么

- 不是机动建议。它只说明两个物体会靠近；怎么处置属于运营方。
- 归属上不对称。双方看到同一个事件，各自带自己的申报状态——那是协同信号，不是计算量。
- 不是编目公告。CDM 说的是星历；编目自身的交会是另一份数据（见应用里的**交会事件**）。

## 本部署怎么算出这条 CDM

下面是筛查的实际配置，写出来是因为"无法追问的概率"不构成证据：

| 参数 | 取值 |
|---|---|
| 筛查盒，径向 | ± 2 km |
| 筛查盒，沿迹方向 | ± 44 km |
| 筛查盒，法向 | ± 51 km |
| 事件聚合窗口 | 20 分钟 |
| 碰撞概率 | 二维 Alfano 法，投影到交会面 |
| 轨迹最短跨度 | 6 个状态点、42 秒、不超过 21 天 |

筛查盒是刻意各向异性的：沿迹方向的不确定度比另外两向大一个量级，用一个各向同性的盒子
去筛，要么漏掉真实交会，要么被候选淹没。聚合窗口则是"一次接近 = 一个事件"的实现方式。

# 架构与内部机制

## 一条链

API 暴露的一切都由同一条链产生，每一段都可查：

```
运营方 ──拥有──> 对象 ──拥有多条──> 星历 ──与之筛查──> 事件 ──承载──> CDM
```

| 阶段 | 存什么 | 通过哪里访问 |
|---|---|---|
| 运营方 | 一行记录，含配额 `max_objects` | `/api/v1/operator` |
| 对象 | 名称、NORAD 编号、**硬体半径**、可机动性 | `/api/v1/object` |
| 星历 | 上传的原始字节 + 元数据 | `/api/v1/trajectory` |
| 事件 | 一对对象及它们之间的 CDM | `/api/v2/event/:id` |
| CDM | 每次筛查一条消息 | `/api/v2/cdm` |

## 上传之后发生什么

1. **校验。** 解析文件，格式靠内容识别。状态点少于 6 个、或整段结束于 24 小时之前的
   文件会被拒绝，并逐条给出理由。
2. **存储。** 字节原样落地。`GET /api/v1/trajectory/:id` 返回的就是上传时的内容，
   经本 API 的格式往返无损。
3. **排队。** 创建筛查任务，`screened_status` 报告进度。
4. **筛查。** 对该星历做传播，在时间重叠窗口内与编目比对，发现交会就产出 CDM。
5. **聚合。** 同一对物体、同一次接近的多次 CDM 归为一个**事件**，于是估计的历史可见，
   而不是一堆散落的消息。

## 为什么要留原始字节

数据库存的是**结论**——这个物体在那个时刻在这里。上传的文件是**证据**。没有它，
上游改了星历无法察觉，争议交会在下次上传覆盖之后也无法复核。两者都留着，
API 也两者都能取。

## 背后的编目

筛查需要对照物。本部署用四个公开源（Space-Track、Spacebook、ESA DISCOS、KeepTrack）
加一层补充数据构建参考编目，**编目**分组下的页面展示的就是它。那是**物体**的编目，
不是星历的编目：它有根数与物理属性，没有机动计划。

## 确定性

同样的输入筛查两次，得到的 CDM 逐位相同，包括 `tca_gps_nanos`。这条值得写下来：
一个答案取决于"哪个 worker 答的"的交会服务，没法拿去和别的运营方对账。

## 已知边界

| 边界 | 后果 |
|---|---|
| 文件里没有协方差 → Pc 为 `null` | 仍然报最近距离，但不臆造概率 |
| 对方没有近期星历时为单边筛查 | 作为对编目根数的事件报告，不报概率 |
| `hypothetical` 上传永不进入筛查 | 它的用途是回答"假如"，不是发告警 |

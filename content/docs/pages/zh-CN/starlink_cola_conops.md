# 避撞运行概念

大型星座背后的运行概念，从本 API 的客户端能看到的那一侧来讲。

## 那个环

```
编目 ──> 筛查 ──> CDM ──> 决策 ──> 机动 ──> 新星历 ──> 再筛查
```

每一根箭头都是 API 暴露的数据，这也是它写在这里而不是写在白皮书里的原因：

| 环节 | 在哪里可见 |
|---|---|
| 编目 | **编目**页面，按源的覆盖率 |
| 筛查 | 星历上的 `screened_status` |
| CDM | `/api/v2/cdm` |
| 决策 | 事件上的 `claim_status_*` |
| 机动 | 一条 `upload_type: definitive` 的新星历 |
| 再筛查 | 同一事件的新 CDM |

## 自动化可以决定什么

筛查服务能算概率，但它不能决定去烧别人卫星的推进剂。本部署划的线：

| 服务做 | 服务不做 |
|---|---|
| 发现交会并发布 CDM | 推荐机动方案 |
| 把消息聚合成事件 | 判定某事件是否可接受 |
| 记录运营方声明的申报 | 从观测到的行为推断申报 |
| 算不出 Pc 时返回 `null` | 用一个默认概率顶替 |

最后那一对最需要守住。编造的申报和默认的 Pc 都长得像信息，而两者都会被据以行动。

## 运营方之间的协同

交会是双向的：双方用各自的星历、各自的协方差筛查同一对物体，算出的 Pc 不会完全相等——
假装它相等，是任一方都能证伪的谎。

让协同成立的，是双方都能看到：

1. 同一个事件标识；
2. 各自的申报，以及最近一次更新时间；
3. 显示估计如何变化的消息历史。

所以 API 暴露历史，而不只是当前状态。一个数字没法讨论，一串数字可以。

## 本部署的立场

这里没有挂任何星座。筛查流水线在、事件与 CDM 模型已实现，但没有运营方上传过星历——
所以 `/api/v2/cdm` 返回空的 `result`，而编目的公开发布 CDM 在应用的**交会事件**页可见。
那是两份不同的数据，应用里也是这样标注的。

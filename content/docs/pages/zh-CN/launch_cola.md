# 发射与早期任务阶段

任务最初几小时最难预测，后果也最集中：物体被释放进一个已经装着数千个被跟踪碎片的
壳层，而运营方自己的星历还没发布。

## 把问题说直白

| 阶段 | 知道什么 | 不知道什么 |
|---|---|---|
| 上升段 | 发射窗口、目标轨道 | 跟踪开始前，真实状态一无所知 |
| 分离部署 | 物体数量与大致间隔 | 单独的状态；谁有处置权 |
| 早期轨道 | 首批根数到达 | 卫星是否还能机动 |
| 正常运行 | 已发布星历 | —— |

没有星历的物体无法筛查；服务能做的是说明首批根数何时到达、它们意味着什么。

## 本部署提供什么

编目相关页面带有被跟踪的物体总量，包括给出"什么正在落下来"的 60 天与再入数据。
待发射与其统计在**发射与解体**页，来源是 KeepTrack，不是本服务自行计算。

```bash
# 一个轨道类型的编目对象数
curl -s 'http://127.0.0.1:3000/api/v1/catalogue/choice?regime=LEO' | head -c 200
```

## 为什么早期避撞不一样

只要预警足够，还能机动的卫星几乎躲得开一切。早期阶段真正的约束不是速度增量，
而是**授权**：在卫星被宣布进入正常运行之前，团队是否被允许依据一条告警行动。
那是流程问题，再多的数据也解决不了它——这也正是 API 记录申报状态、而不去臆造的原因。
